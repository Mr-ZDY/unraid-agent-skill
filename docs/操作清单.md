## 操作分级

| 级别 | 操作 | 策略 |

## 容器部署流程（用户铁律）

1. **来源判定**：CA 官方/可信 → 绿色通道；第三方 → 红色警告 + 用户明确许可
2. **端口规则**：涉及新端口 → 列出已占用端口 + 推荐 3 个 → **必须用户提供** → 校验空闲
3. **确认门**：部署摘要（应用/镜像/来源/端口/卷/环境变量）→ 用户确认
4. **执行**：SSH 自动执行（docker create + docker start，含 dockerman 标签 → WebGUI 可见）
5. **审计**：记录应用名/来源级别/端口/结果

## 容器卸载流程

1. 查询容器数据卷路径（mounts）
2. 摘要展示 + 有数据卷时提示备份
3. 确认门 → SSH 执行（docker stop + docker rm）→ 审计

## 权限矩阵（API 密钥角色）

- 查询类：VIEWER 够用
- 容器管理/部署：**必须 ADMIN**（CONNECT 无 DOCKER 写权限 —— 2026-08-09 实测踩坑）

## 已知坑位（踩坑沉淀）

### GPU 状态判定（2026-08-09）
- **误判案例**：`docker inspect` 显示 `Devices=[] Gpus=[]` 就断言"容器没吃 GPU" → 错误
- **真相**：`--runtime=nvidia` 容器的 GPU 由 NVIDIA Container Toolkit 在**容器启动时动态注入**，静态 inspect 不显示属正常
- **正确判定**（info_gpu.py 已实现）：
  1. 宿主层：`nvidia-smi`（驱动/温度/利用率）+ `lspci` + `/dev/dri`
  2. 容器层：`docker exec <容器> ls /dev/nvidia0` 或容器内 nvidia-smi
  3. 应用层：ML 等服务日志看执行引擎（immich 日志显示 `CUDAExecutionProvider`）
- **核显**：插了独显时主板默认屏蔽 Intel 核显（PCI 枚举不到），属正常；要用核显需 BIOS 开启 iGPU
- **API 参考**：`info { devices { gpu } }` 查询有内部 bug（InfoGpu.type 空值报错），GPU 状态走 SSH 最可靠

### macvlan 容器与宿主隔离（2026-08-09）
- **现象**：moviepilot（bridge 容器）连不上 qbittorrent（br0/macvlan 独立 IP 192.0.2.200:6555），宿主 ping 也 100% 丢包
- **原理**：macvlan 特性 —— 宿主及经宿主转发的流量**无法访问 macvlan 容器**；macvlan 容器之间可经交换机互通
- **解决（保持 macvlan 独立性）**：创建共享内部 bridge 网络，两个容器各加一块内网网卡，用 Docker DNS 互通：
  ```
  docker network create mp-net
  docker network connect mp-net qbittorrent      # 保留 br0/IP 不动
  docker network connect mp-net moviepilot-v2
  # moviepilot 下载器地址用 http://qbittorrent:6555（内网 DNS）
  ```
- ⚠ **维护注意**：容器经 unRAID 模板重建后 mp-net 挂载会丢，需重新 connect
- **为什么不迁 bridge**：qbittorrent 在 br0 是刻意设计（旁路由按 IP 限速 + BT 流量直连不走代理），迁 bridge 不可接受

### qbittorrent 限速为有意配置（2026-08-09 确认，勿改）
- 备用速率调度器 100KB/s + max_active_uploads=1 + DHT 关闭 = **用户故意设置**（控制上传带宽）
- 排查结论：上传 75KB/s 属正常预期，不是故障；公网 BT 端口可达、.205 在 OpenClash 绕过代理名单（直连出网）
- 以后诊断 qb 上传慢时：先对照此条，别再当问题排查
